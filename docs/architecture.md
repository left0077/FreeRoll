# 架构决策记录

## ADR-1: 前端框架 — React (Vite)

**决定**：React + Vite + TailwindCSS，不做 SSR。

**理由**：纯 SPA 足够，无 SEO 需求。

## ADR-2: 后端 — FastAPI

**决定**：Python FastAPI。

**理由**：WebSocket 原生支持，DeepSeek Python SDK 生态成熟。

## ADR-3: 实时通信 — WebSocket

**决定**：单一 WebSocket 连接，复用同一通道传输多种消息类型。

## ADR-4: AI 记忆策略 — 全文保留

**决定**：整个对局对话历史全文保留。

1 小时游戏约 50K tokens，不到 DeepSeek 1M 上下文的 5%，无需任何裁剪。

## ADR-5: 用户体系

**决定**：房间码 + 昵称进入，localStorage 记住昵称。无注册无登录。

## ADR-6: 部署策略

**决定**：前端 GitHub Pages，后端 ngrok 内网穿透。

## ADR-7: 移动端策略

**决定**：纯响应式网页，按钮掷骰，不做摇一摇。

## ADR-8: 回合机制 — AI 动态分配

**决定**：不由系统固定轮转顺序，由 AI 根据叙事决定"现在轮到谁"。

- AI 在叙事末尾用 `[NEXT:角色名]` 标记指定下一个行动的玩家
- 如果 AI 未标记，回退到加入顺序轮转
- 房主可以手动跳过某人的回合

**理由**：跑团天然是"谁该动就谁动"，不是固定顺序。怪物突袭时 AI 可以直接点名。

## ADR-9: 角色创建 — 双模式

**决定**：根据剧本类型，玩家可自创或选预设角色。

- **自创**：AI 辅助车卡，玩家写一句话描述 → AI 生成角色卡 → 玩家编辑确认
- **预设**：世界模组可自带预设角色，玩家直接认领（如"《诡秘之主》"剧本自带克莱恩、奥黛丽等）
- 房主创建世界模组时决定允许哪种模式

## ADR-10: 游戏结束 — AI 判定

**决定**：AI 在叙事中判断剧情是否自然收尾，提示房主"是否可以结束？"。房主确认后结束。

## ADR-11: 回溯机制

**决定**：房主可回溯到任意历史回合。技术实现：

1. 服务端维护每回合开始时的**角色状态快照**（存 Redis，键 `room:{code}:snapshot:{turn}`）
2. 回溯时：恢复快照 + 删除该回合之后的 chat_message 和 dice_log
3. 玩家重新从回溯点继续游戏

**代价**：每回合多存一份 JSON 快照（6 角色 × 500 字节 = 3KB/回合，180 回合 ≈ 540KB，可忽略）。
